---
title: Guardrails in PURISTA
description: Apply Harness content controls inside a service without weakening PURISTA authorization or delivery guarantees.
---

Guardrails protect content crossing a Harness agent boundary. PURISTA still
owns identity, authorization, service contracts, command/queue semantics, and
business decisions. Use both layers.

| Boundary | Primary control |
| --- | --- |
| Request into a service | PURISTA schema and authorization |
| Input/output/tool/retrieval content in a Harness agent | Guardrails |
| Tool side effect | Tool schema, governance/approval, and service authorization |
| Durable delivery and retry | PURISTA queue/worker plus idempotent business action |

Attach guardrails to the default-loop agent inside your harness composition.
When a PURISTA-owned workflow invokes that agent, the guardrail applies to the
agent loop. If framework orchestration retrieves documents, filter the selected
chunks explicitly before they enter the guarded agent; vector storage and
retention stay application-owned.

Keep fail-closed detector errors visible through stable error kinds and OTel
spans, never through inspected content. The Harness owns GenAI/model/tool and
guardrail telemetry; PURISTA records its service and agent-wrapper telemetry
around that work without duplicating token metrics.

## Bind Guardrails to a service agent

The optional package remains in the application composition root. Core does not
need an addon dependency or a second configuration surface: give
`setHarnessAgent(...)` the normal Harness definition with `guardrails: rails`.

```ts title="claimsAnswerAgentBuilder.ts"
import { z } from 'zod'
import {
  createSensitiveDataActions,
  defineGuardrailAction,
  defineGuardrails,
} from '@purista/harness-guardrails'
import { createNativePrivacyDetector } from '@purista/harness-guardrails-native-privacy'
import { claimsV1ServiceBuilder } from '../claimsV1ServiceBuilder.js'

const rails = defineGuardrails({
  config: {
    rails: {
      input: {
        flows: ['deny prompt override', 'mask sensitive data on input'],
      },
      output: {
        flows: ['remove internal note'],
      },
    },
    sensitiveData: {
      input: {
        entities: ['EMAIL_ADDRESS'],
        maskToken: '<REDACTED>',
        scoreThreshold: 0.8,
      },
    },
  },
  actions: {
    ...createSensitiveDataActions({
      detector: createNativePrivacyDetector({ id: 'claims-local-privacy' }),
    }),
    'deny prompt override': defineGuardrailAction({
      phase: 'input',
      valueSchema: z.string(),
      mayTransform: false,
      evaluate: ({ value }) =>
        typeof value === 'string' && value.includes('ignore previous instructions')
          ? { decision: 'block', reasonCode: 'prompt_override' }
          : { decision: 'allow' },
    }),
    'remove internal note': defineGuardrailAction({
      phase: 'output',
      valueSchema: z.string(),
      evaluate: ({ value }) =>
        typeof value === 'string'
          ? {
              decision: 'transform',
              target: 'bot_message',
              value: value.replaceAll('[internal]', ''),
              reasonCode: 'internal_note_removed',
            }
          : { decision: 'allow' },
    }),
  },
})

export const claimsAnswerAgentBuilder = claimsV1ServiceBuilder
  .getAgentQueueBuilder('claimsAnswer', 'Answers a claims question safely')
  .addPayloadSchema(z.string().min(1))
  .addOutputSchema(z.string())
  .addModel('assistant', { capabilities: ['object'] as const })
  .setHarnessAgent({
    model: 'assistant',
    input: z.string().min(1),
    output: z.string(),
    instructions: 'Answer only with approved claims information.',
    guardrails: rails,
  })
```

Bind only the normal Harness model at service startup. The rail configuration
and its detector are already part of the attached definition; they are not
passed through `ai` and are never inferred from provider configuration.

```ts title="bootstrap.ts"
const claimsService = await claimsV1ServiceBuilder
  .addAgentDefinition(await claimsAnswerAgentBuilder.getDefinition())
  .getInstance(eventBridge, {
    queueBridge,
    ai: {
      models: {
        assistant: {
          provider,
          model: 'claims-assistant',
          capabilities: ['object'],
        },
      },
      telemetry: { contentCaptureMode: 'NO_CONTENT' },
    },
  })
```

Use a private Presidio sidecar or reviewed local NER detector instead when the
native subset is insufficient. Keep its endpoint/authentication or local-model
integrity configuration in bootstrap code, not a separate policy format.

## Human approval is a separate workflow

For an immediate sensitive tool call, a permission or policy can demand
`require_approval`. One `ai.governance.approval` provider handles the collected
demands and returns `approved` or `rejected`, optionally with a content-free
`reasonCode`. Honour the supplied `signal` and `deadline`; a late result cannot
admit the handler. A content rail's `block` is never an approval request.

A review that can outlive the current worker belongs to the owning service:
persist an application review task, accept an authenticated compare-and-set
decision, and signal the Harness external wait. On resume, bind and reauthorize
the approved action before atomically claiming an immutable execution. Execute
with the claim's stable idempotency key and persist its receipt. Recovery reuses
that claim/receipt; a plain read followed by execution is unsafe. No in-process
Promise should hold the queue worker open for a human response. See
[human review](/handbook/harness/orchestrate-work/human-review/).
