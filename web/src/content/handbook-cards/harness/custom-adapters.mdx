## Start with the existing ports

An adapter is infrastructure behind the Harness session API. It is not a tool,
workflow, plugin loader, or a place to add domain policy. For the claims-review
example, select the smallest port that owns the integration:

| Requirement | Existing core option | Extend this port when | Required evidence |
| --- | --- | --- | --- |
| Provider-neutral model calls | First-party `@purista/harness-<provider>` addon | The provider is not already supported | Provider contract tests and a scripted client |
| Conversation history and run records | `InMemoryHarnessStorage`, `SqliteHarnessStorage` for one host | History/runs must use your database or tenancy model, or durable workflows need multi-instance safety | State-store/durable-state contract tests and migration/retention tests |
| Scoped facts or semantic recall | Default in-memory engine | Memory needs persistence, cross-instance use, text search, or vector recall | Memory-engine contract tests and scope-isolation tests |
| Files and optional command execution | `inMemorySandbox()`, `bashSandbox()`, local durable sandbox | You need containers, microVMs, remote runners, or immutable mounts | Sandbox contract plus isolation/cancellation tests |
| Restart-safe workflow checkpoints | `InMemoryHarnessStorage` or `localDurableExecution` | Workers need distributed leases or cloud persistence | Storage/workspace contracts and replay tests |
| External capability | TypeScript tool or `mcp_http` / `mcp_stdio` | The capability has its own tool/server protocol | Tool tests plus authorization and outage tests |

Keep a portable model alias, tool schema, agent, and workflow while swapping an
adapter. The claims workflow should still call `ctx.agents.assessor(...)` and
`ctx.memory.tenant().read(...)`; it should never acquire a database client or a
provider SDK itself.

## Package and composition pattern

Put a reusable integration in its own package, for example
`@acme/harness-memory-postgres`. Its factory validates its own configuration,
declares only capabilities it actually implements, and returns a `MemoryEngine`.
The application owns credentials and chooses the engine at the
composition root.

```ts
import { defineHarness } from '@purista/harness'
import { postgresClaimsMemoryEngine } from '@acme/harness-memory-postgres'

const memory = postgresClaimsMemoryEngine({
  connectionString: process.env.CLAIMS_MEMORY_DATABASE_URL!,
  table: 'claim_memory'
})

const harness = defineHarness({ name: 'claims-review' })
  .memory(memory)
  .requires(['memory.kv', 'memory.persistent', 'memory.multi_instance'])
  // models, tools, agents, and workflows
  .build()
```

Use `.requires(...)` for capabilities the application cannot operate without.
It prevents a misleading startup where an adapter silently falls back to
process-local behavior. Do not include provider credentials, connection strings,
raw prompts, evidence, or tool data in adapter diagnostics, logs, spans, or
metrics.

## Build a provider adapter around `BaseModelProvider`

Provider adapters should extend `BaseModelProvider`. It owns cancellation,
timeouts, retry orchestration, normalized errors, safe logs, spans, and usage
metrics. The adapter maps only the provider SDK request/response and returns
the provider-neutral response.

```ts
import {
  BaseModelProvider,
  type JsonValue,
  type ObjectRequest,
  type ObjectResponse
} from '@purista/harness'

type ClaimsSdk = {
  generateObject(input: {
    model: string
    messages: unknown
    schema: JsonValue
    signal: AbortSignal
  }): Promise<{ object: JsonValue; inputTokens: number; outputTokens: number; stopReason?: string }>
}

export class ClaimsModelProvider extends BaseModelProvider {
  public constructor(private readonly client: ClaimsSdk) {
    super({ id: 'acme_claims', genAiSystem: 'acme' })
  }

  protected async doObject<T extends JsonValue = JsonValue>(
    request: ObjectRequest<T>
  ): Promise<ObjectResponse<T>> {
    const response = await this.client.generateObject({
      model: request.model,
      messages: request.messages,
      schema: request.schema,
      signal: request.signal
    })

    return {
      object: response.object as T,
      usage: {
        inputTokens: response.inputTokens,
        outputTokens: response.outputTokens,
        totalTokens: response.inputTokens + response.outputTokens
      },
      finishReason: 'stop',
      outcome: { finishReason: 'stop', providerFinishReason: response.stopReason }
    }
  }
}
```

Declare only `object` on an alias backed by that implementation. Do not claim
`tool_use`, streaming, embeddings, reranking, or multimodal input until the
adapter implements and tests the matching operation. Preserve provider-reported
usage, cache, and reasoning token details when available; do not estimate cost
or invent tokens. `BaseModelProvider` adds the model span and normalized error
shape around the `doObject` call.

```ts
import { modelProviderContract } from '@purista/harness/testing'

modelProviderContract(
  () => new ClaimsModelProvider(createScriptedClaimsSdk()),
  { capabilities: ['object'] }
)
```

Use a scripted offline SDK in this contract suite. Add integration tests for
SDK-specific pagination, rate limiting, cancellation, and raw finish reasons;
keep live-provider tests explicit and outside normal CI.

## Implement state and memory independently

`HarnessStorage` persists sessions, messages, runs, and run events. It is the right
adapter for claims conversation history and run audit metadata. Implement the
complete port or extend `HarnessStorage`; partial persistence creates
inconsistent session lifecycle behavior. If you enable
`defaults.historyRetention`, implement `replaceMessages` atomically so whole
turns are trimmed without a read/clear/append race.

`MemoryEngine` is a separate typed persistence boundary. It receives a
canonical scope and record from core; it cannot open a session or choose a
model. For a claims system, a tenant-scoped profile must not be reachable from a
different tenant merely because two sessions share an agent ID. Respect
`ctx.signal` on every backend request and let core own standard telemetry,
identity binding, model routing, and error wrapping.

```ts
import { memoryEngineContract } from '@purista/harness/testing'
import { postgresClaimsMemoryEngine } from '@acme/harness-memory-postgres'

memoryEngineContract(() => postgresClaimsMemoryEngine({
  connectionString: process.env.TEST_DATABASE_URL!
}))
```

Add application tests around the port contract: tenant isolation, TTL expiry,
search-result authorization, deletion, and data residency. Do not use memory
as a replacement for the authoritative claim record.

### Storage lifecycle and logger contracts

Implement `HarnessStorage` directly. A concrete adapter must implement session
upsert/close, ordered message append/list/clear, run create/finish/read/list,
and event append/list. Implement `replaceMessages(sessionId, messages)` as one
database transaction when history retention is enabled—never as an unlocked
clear followed by append.

```ts
import type { HarnessStorage } from '@purista/harness'
import { harnessStorageContract } from '@purista/harness/testing'
import { PostgresHarnessStorage } from '@acme/harness-storage-postgres'

const createStorage = (): HarnessStorage =>
  new PostgresHarnessStorage({ connectionString: process.env.TEST_DATABASE_URL! })

harnessStorageContract(createStorage)
```

The optional `configureHarnessContext` hook receives the logger, telemetry,
and harness name. Use them only for content-free backend spans or
safe normalized diagnostics. `close()` must drain pools predictably so
`harness.shutdown()` can report a controlled shutdown failure.

A custom logger implements the complete `Logger` surface (`trace` through
`fatal`) and `child(bindings)`. Make binding merges deterministic and redact at
the sink as a final defense. Test it with the public contract before attaching
it through `.logger(...)`:

```ts
import { loggerContract } from '@purista/harness/testing'

loggerContract(() => createClaimsJsonLogger({ destination: testSink }))
```

The logger contract checks every level, child logger behavior, and—when the
test logger exposes records—one RFC3339 timestamped record per call. Never make
captured test records contain raw prompts, evidence, tool values, or secrets.

## Build a sandbox or durable adapter deliberately

A `Sandbox` opens one session-owned filesystem/execution boundary. It must
declare whether an executor is available; a file-only adapter returns
`executor: 'unavailable'`. Implement `spawn(...)` only when the runtime can
own a long-lived MCP process safely. Snapshot, resume, and hibernate are
optional capabilities, not assumptions.

```ts
import { sandboxContract, sandboxSnapshotContract } from '@purista/harness/testing'

sandboxContract(() => createClaimsContainerSandbox(), { executor: 'available' })
sandboxSnapshotContract(() => createClaimsSnapshotSandbox())
```

Test that the sandbox enforces mounts, network policy, process limits,
cancellation, cleanup, and tenant isolation—not merely that a command runs.
The core `bashSandbox()` is an in-process execution helper, not an isolation
boundary for untrusted documents or commands.

A `HarnessStorage` owns run leases and committed step checkpoints. A durable
workspace owns workspace lifecycle, snapshots, retention, encryption metadata,
quota reporting, and cleanup. Keep the two ports separate: a sandbox
snapshot alone does not make a workflow replayable after a restart.

```ts
import { durableWorkspaceContract } from '@purista/harness/testing'
import { claimsWorkspaceStore } from '@acme/harness-workspace-postgres'

durableWorkspaceContract(() => claimsWorkspaceStore({
  connectionString: process.env.TEST_WORKSPACE_DATABASE_URL!
}))
```

For a production adapter, test a process restart after every durable step,
lease contention, retry of a failed run with the same run ID, quota exhaustion,
orphan cleanup, retention expiry, and no raw workspace content in telemetry.

## Adapter author checklist

1. Choose one port; do not bundle provider, business policy, and queue delivery
   into an adapter.
2. Validate adapter configuration at construction and keep secrets out of error
   details.
3. Declare only truthful capabilities and use `.requires(...)` in the
   application for mandatory ones.
4. Honor `AbortSignal` and close adapter-owned pools/processes in `close()`.
5. Reuse `BaseModelProvider` where it fits and implement `HarnessStorage` once
   than reimplementing common logging, telemetry, timeout, and error behavior.
6. Run the matching public contract suite with deterministic fakes.
7. Add adapter-specific integration tests for the backend's failure and
   lifecycle semantics.
8. Verify content-free telemetry: IDs, durations, usage, and normalized errors
   are useful; prompts, evidence, tool payloads, credentials, and files are
   not emitted.

Return to [Sandboxing & MCP](/handbook/harness/sandboxing-and-mcp/) for the
execution boundary, or [Durable Workflows & Queues](/handbook/harness/durable-workflows-and-queues/)
for the replay and delivery design.
