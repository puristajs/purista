## Prerequisites

Complete [Observability & Operations](/handbook/harness/guide/observability-operations/).
This final guide translates an application requirement into an explicit Harness
port. Start local and in memory, then replace only the boundary that needs
production behavior.

## Adapter choices

| Need | Harness boundary | Start local | Production decision |
| --- | --- | --- | --- |
| Provider-neutral inference | Model provider addon | One provider adapter and a truthful model alias | Select a provider adapter per deployment; keep aliases stable. |
| Persisted history and runs | `StateStore` | In-memory state | Own retention, deletion, tenant isolation, encryption, and migrations. |
| Scoped memory | `MemoryAdapter` | Sandbox memory | Select scope, search, TTL, and data residency deliberately. |
| File access or commands | `Sandbox` | In-memory/files-only sandbox | Isolate process, filesystem, network, mounts, timeouts, and cleanup. |
| Restart-safe workflow state | Durable runtime, workspace store, checkpoints | In-memory durable helpers | Provision durable storage, leases, quotas, cleanup, and recovery. |
| External tool server | MCP through sandbox or HTTP boundary | Local test fake | Own authentication, endpoint policy, schema validation, and availability. |
| Privacy inspection | `SensitiveDataDetector` adapter | Native privacy fake/detector | Choose native, a private Presidio sidecar, local NER, or an injected implementation. |

Do not make a direct model, storage, or sandbox SDK call from an agent just to
avoid an adapter decision. That bypasses typed capabilities, cancellation,
telemetry, and the composition-root policy that make the Harness reviewable.

## Choose durability by recovery requirement

Use an application queue for delivery and business retries. Use Harness durable
execution when a *workflow run* must retain resumable workspace/checkpoint state
between steps. They solve different problems.

```ts
const session = await harness.getSession(`claims:${claimId}`)
try {
  const result = await session.workflows.review_claim.prompt(
    { claimId },
    { durable: { runId: `claim-review:${claimId}` } }
  )
  await claimsRepository.recordDecision(result)
} finally {
  await session.release()
}
```

Before enabling `durable`, configure and verify the required durable runtime,
workspace store, and checkpoint store. Use stable run IDs only for an
idempotent business operation. A direct agent call cannot be made durable;
place long-running orchestration in a workflow, and use a queue/worker when an
HTTP request must return before the workflow completes.

## Extend an adapter without leaking provider types

Implement the relevant exported port in a dedicated package or application
adapter. Its constructor should validate configuration and capability claims;
the Harness composition root registers the instance. Keep credentials,
connection pooling, retries, and transport-specific errors inside the adapter,
then return the normalized port result.

For example, a durable workspace adapter must pass the shared contract suite
before it is used by application workflows:

```ts
import { durableWorkspaceStoreContract } from '@purista/harness/testing'
import { createWorkspaceStore } from './workspace-store.js'

durableWorkspaceStoreContract(() => createWorkspaceStore({ connectionString: process.env.WORKSPACE_DB_URL! }))
```

Run this contract suite in the adapter package. Application tests should then
cover the desired pause, resume, retention, quota, and cleanup behavior without
retesting the port protocol itself.

## Production checklist

1. Provide provider, state, sandbox, memory, and durable adapters explicitly;
   do not rely on development defaults.
2. Validate all required adapter capabilities during startup with
   `.requires(...)`; fail readiness before accepting traffic when a mandatory
   runtime feature is absent.
3. Keep secrets in a secret manager or deployment environment. Do not emit
   them to logs, spans, run events, skills, or fixtures.
4. Bound model, tool, skill, run, queue, and storage behavior with independent
   timeouts, retry policies, quotas, retention, and idempotency keys.
5. Run a deterministic fake-provider smoke test, then an explicitly opt-in live
   provider smoke test. Verify `harness.shutdown()` on graceful shutdown.
6. Verify traces connect application request, session, workflow, agent, model,
   tool, and guardrail spans. Model/provider/token attributes are available on
   nested model spans only when the provider reports them.

## Public API and package map

The website is the public documentation destination. The package surface is
organized by responsibility:

| Package | Use it for |
| --- | --- |
| `@purista/harness` | Builder, sessions, adapters/ports, errors, telemetry, evaluation helpers. |
| `@purista/harness/testing` | Deterministic model, state, sandbox, memory, telemetry, and contract test fakes. |
| `@purista/harness-<provider>` | One independently installed model-provider adapter. |
| `@purista/harness-guardrails` | Optional portable rail config, rail actions, and detector interfaces. |
| `@purista/harness-guardrails-presidio` | Private-sidecar adapter for the original Presidio Analyzer. |
| `@purista/harness-guardrails-native-privacy` | Deterministic in-process local detection for the documented identifier subset. |
| `@purista/harness-guardrails-local-ner` | Separately installed local model-based NER detector. |
