title: Human Review Gates
description: Pause a durable AI workflow for an authenticated, application-owned decision without losing checkpoints or re-running side effects.

## What this capability does

Harness provides a small, provider-neutral checkpoint-and-signal primitive. It
does **not** provide a reviewer UI, identity system, database table, HTTP
endpoint, notification channel, or domain authorization policy. Your PURISTA
application owns those concerns; Harness owns safe suspension and replay.

```mermaid
sequenceDiagram
  participant W as Durable workflow
  participant H as Harness runtime
  participant R as App review task
  participant U as Authorized reviewer
  W->>H: ctx.step("prepare", ...)
  H-->>W: checkpointed result
  W->>R: create task (business-key idempotent)
  W->>H: ctx.externalWait.wait(safe reference)
  H-->>W: ExternalWaitPendingError; run status waiting
  U->>R: guarded compare-and-set decision
  R->>H: signal(waitId, eventId, outcome)
  W->>H: invoke same durable runId
  H-->>W: replay prepare; return terminal outcome
  W->>R: reread, reauthorize, compare action digest
  W->>R: idempotent final domain command
```

The workflow never holds a Promise or trace open while waiting. A later worker
invokes the same `durable.runId`; completed `ctx.step(...)` work replays from
the durable checkpoint.

## Smallest secure setup

`localDurableExecution()` supplies SQLite-backed state, runtime, checkpoints,
and the external-wait adapter for Node.js and Bun. Production deployments may
provide their own adapter with the same contract.

```ts
const durable = localDurableExecution({ root: '.purista/reviews', exec: false })

const harness = defineHarness({ name: 'payment-review' })
  .state(durable.state)
  .runtime(durable.runtime)
  .externalWait(durable.externalWait)
  .requires(['runtime.persistent', 'external_wait.durable', 'external_wait.signal'])
  // models, agents, and workflow definitions
  .build()
```

Inside the workflow, create the **application review task first** using a
stable business key. Its immutable descriptor must include the action schema,
policy/definition version, target revision, expiry, delivery idempotency key,
and canonical action digest. Store question text, proposed values, and reviewer
comments only in the application task record—not in the Harness wait request.

```ts
const proposal = await ctx.step('proposal-v1', () => reviewTasks.create({
  businessKey: `payment:${ctx.input.paymentId}:v1`,
  actionDigest: canonicalDigest(ctx.input),
  definitionVersion: 'payment-v1',
  expiresAt: '2026-09-01T12:00:00.000Z'
}))

const wait = await ctx.externalWait.wait({
  waitId: proposal.waitRef,       // opaque, stable application reference
  kind: 'human_review',
  schemaVersion: 'payment-review-v1',
  definitionVersion: 'payment-v1',
  deadline: proposal.expiresAt
})

if (wait.status !== 'approved') return { status: wait.status }

const approved = await reviewTasks.readApproved(proposal.businessKey)
if (!approved || approved.actionDigest !== canonicalDigest(ctx.input)) {
  throw new Error('Approved review is stale or does not bind this action')
}
await payments.executeIdempotently({ ...ctx.input, idempotencyKey: ctx.runId })
```

On the first pending result, `wait()` throws `ExternalWaitPendingError`. Treat
that as successful queue handling: persist/publish the task through your normal
outbox, then stop the delivery. Do not convert it into a failed business action
or leave a worker blocked. Once an authenticated reviewer commits a compare-and
set decision, deliver exactly one terminal signal:

```ts
const result = await durable.externalWait.signal({
  waitId: task.waitRef,
  eventId: decision.outboxEventId,
  outcome: decision.outcome // approved | rejected | expired | cancelled
})
// applied, duplicate, already_terminal, or not_found: all are deterministic.
```

For a wrapped PURISTA attached Harness workflow, opt into `ai.durableWorkflows`
and pass `ai.onExternalWaitPending`. That callback is the explicit delivery
acknowledgement point: commit or publish the already-created application task
and return an output that your agent schema models as `waiting`. Without it,
the pending error intentionally propagates instead of being mistaken for a
successful queue completion.

## Rules that keep approval meaningful

1. Authenticate and authorize the reviewer in a normal PURISTA command or
   subscription guard. The adapter never authenticates a signal.
2. Decide with compare-and-set against the pending task revision. Return typed
   stale, already-decided, expired, and not-found outcomes.
3. On resume, reread the task, reauthorize the final side effect, and compare
   the current action digest, target revision, definition version, and expiry.
   Any mismatch fails closed and creates a fresh task.
4. Use an idempotent final command. Durable checkpoints prevent replaying
   completed callback code; they cannot turn an external transaction into a
   universal exactly-once operation.

For immediate approval of a single model tool call, use the existing
`GovernanceApprovalProvider`. It is in-process policy enforcement, not a
long-running business review process.

## Operations and tests

Harness emits `external_wait.requested`, `external_wait.waiting`, and
`external_wait.resolved` events. Its short OpenTelemetry spans include workflow
and run correlation plus kind, schema/definition version, deadline state, and
terminal outcome. They intentionally exclude review content, tool arguments,
comments, and reviewer identity; do not add those values as metric dimensions.

Use `inMemoryExternalWait()` and `inMemoryDurableRuntime()` in deterministic
tests. Cover: pending suspension, restart/replay, approved/rejected/expired/
cancelled outcomes, duplicate and late delivery, stale task revision, changed
action digest, and the idempotent final command. The Harness adapter test does
not replace application authorization or review-task tests.

The repository’s executable `examples/durable-human-review` reference contains
the application-side task store, revision CAS, action descriptor, terminal
signal, resume path, and focused tests. It is deliberately a reference pattern,
not a framework-owned review subsystem.
