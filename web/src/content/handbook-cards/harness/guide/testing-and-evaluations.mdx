## Prerequisites

Build a minimal Harness first. Tests use the same sessions, schemas, agents,
tools, workflows, and rails as production; only adapters and fixtures change.
Never record production prompts, tool values, or credentials to create fixtures.

## Test from the boundary inward

| Level | Prove | Preferred evidence |
| --- | --- | --- |
| Tool unit test | Authorization, validation, and business rules | Invoke the handler with a small fixture |
| Agent integration test | Prompt-to-output and error mapping | `FakeModelProvider` |
| Workflow test | Delegation, branching, side effects, cancellation | Scripted model outcomes and asserted contracts |
| Guardrail test | Allow, transform, block, and failure-closed paths | Detector/action fakes |
| Live smoke test | Provider credentials and deployment wiring | Explicit opt-in environment only |

## Write a deterministic agent test

`FakeModelProvider` is the Harness test adapter. Queue the exact model outcome
before opening a session, then assert the typed result and safe request shape.

```ts
import { expect, test } from 'vitest'
import { z } from 'zod'
import { defineHarness, inMemorySandbox } from '@purista/harness'
import { FakeModelProvider } from '@purista/harness/testing'

test('returns a validated support answer without a provider call', async () => {
  const provider = new FakeModelProvider()
  provider.enqueueObject({
    object: { answer: 'Update the delivery address before dispatch.' },
    usage: { inputTokens: 4, outputTokens: 8, totalTokens: 12 },
    finishReason: 'stop'
  })

  const harness = defineHarness({ name: 'support-test' })
    .sandbox(inMemorySandbox())
    .models({ fake: { provider, model: 'fake', capabilities: ['object'] } })
    .agents(({ agent }) => ({
      support: agent({
        model: 'fake',
        input: z.object({ question: z.string() }),
        output: z.object({ answer: z.string() }),
        builtinTools: false,
        instructions: 'Answer concisely.'
      })
    }))
    .build()

  const session = await harness.getSession('test:customer-42')
  try {
    await expect(session.agents.support.prompt({ question: 'Can I update my address?' }))
      .resolves.toEqual({ answer: 'Update the delivery address before dispatch.' })
    expect(provider.requests).toHaveLength(1)
  } finally {
    await session.release()
    await harness.shutdown()
  }
})
```

For a tool loop, queue a model response containing a tool call and then a final
response. Assert the tool's side effect, Zod validation failure, and a denied
authorization path separately. The fake provider is deterministic but retains
the real Harness loop, telemetry shape, and session lifecycle.

## Test a rail block and detector failure

Use `FakeSensitiveDataDetector`, `FakePresidioSidecar`, or
`FakeLocalNerRuntime` from the selected optional package. Script synthetic
findings, then assert that a block prevents the model or tool side effect. Add
a second case for an adapter fault and assert it fails closed with the stable
error kind. Do not put inspected text in snapshots or expected telemetry.

## Evaluate a prompt change deliberately

An evaluation compares explicit candidate behavior against an explicit dataset
and scorer. Keep datasets, expected output, human labels, and experiment
history in your application or evaluation system. Harness helpers return
aggregate evidence and do not persist prompt or output content by default.

```ts
import { evaluateDeterministicScorer, evaluatePromptCandidates } from '@purista/harness'

const scores = await evaluatePromptCandidates({
  candidates: [
    { id: 'brief', prompt: 'Answer in one paragraph.' },
    { id: 'cited', prompt: 'Answer concisely and cite the policy.' }
  ],
  items: [{ id: 'returns-1', input: { question: 'Can I return this?' }, expected: 'policy' }],
  signal: new AbortController().signal,
  runCandidate: async (candidate, item, signal) => {
    signal.throwIfAborted()
    return runSupportCandidate(candidate.prompt, item.input)
  },
  scorer: target => evaluateDeterministicScorer({
    type: 'contains', path: '/answer', value: String(target.expected), caseInsensitive: true
  }, target)
})
```

Start with schema validity, required citations, allowed tool use, policy
outcome, latency budgets, and domain rules. Add model judges or human review
only after documenting their criteria, cost, and failure path. Keep a live
provider smoke test separate from CI's deterministic suite.
