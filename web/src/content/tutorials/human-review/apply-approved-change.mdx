---
title: Apply the current approval once
description: Check approval, expiry, version, and expected fee together before changing the synthetic fee.
order: 165
status: published
---

The original proposer calls:

```text title="Generated local route"
POST /api/v1/fee-changes/:proposalId/apply
```

The store checks all of these conditions before it writes the new fee:

- the request names the proposal's current version;
- the proposal is approved for that same version;
- the proposal has not expired;
- the account fee still equals the value captured when the proposal was made;
- the caller is the original proposer.

On success it sets the current fee and changes the proposal state to
`applied`. A repeated apply request then returns `409`, so it does not
write the fee twice.

The in-memory method puts these checks and its update in one synchronous
state transition. A production store must make the equivalent conditional
state update and real fee write atomic in its own database transaction. This
example does not settle payments or prove cross-process exactly-once delivery.
