Application code should consume the agent through a normal PURISTA boundary.
Generate the command before editing it.

```bash title="Generate the classification command" replay="project"
npm run add:command -- classify-support-message --service support --service-version 1 --description "Classify one support message with the mounted agent" --non-interactive
```

Use the same schemas at the command boundary and declare the exact target
address with `canInvokeAgent`.

```ts title="src/service/support/v1/command/classifySupportMessage/classifySupportMessageCommandBuilder.ts" write
import {
	classifySupportMessageInputSchema,
	classifySupportMessageOutputSchema,
} from '../../../../../harness/support/agent/classifySupportMessage/classifySupportMessageAgent.js'
import { supportHarness } from '../../../../../harness/support/supportHarness.js'
import { supportV1ServiceBuilder } from '../../supportV1ServiceBuilder.js'

export const classifySupportMessageCommandBuilder = supportV1ServiceBuilder
	.getCommandBuilder('classifySupportMessage', 'Classify one support message with the mounted agent')
	.addPayloadSchema(classifySupportMessageInputSchema)
	.addOutputSchema(classifySupportMessageOutputSchema)
	.canInvokeAgent('Support', '1', 'classify_support_message', supportHarness.contracts.agents.classify_support_message)
	.setCommandFunction(async function ({ agent }, payload) {
		const outcome = await agent.Support['1'].classify_support_message.run(payload, {
			sessionId: `support-message:${payload.messageId}`,
		})
		if (outcome.status !== 'completed') {
			throw new Error('Message classification was interrupted unexpectedly.')
		}
		return outcome.output
	})
```

`canInvokeAgent` adds only the declared address to `context.agent`. The call
always crosses EventBridge, even when Support and the command run in the same
process. This preserves the same location-independent execution model as
commands, streams, and subscriptions.

`.run(...)` returns a `RunOutcome`. The command returns the validated output
only after a completed run. This classifier has no approval or external-wait
step, so an interruption is unexpected here. A later workflow chapter will
show how to expose an interrupted outcome as an ordinary review state rather
than an HTTP 500 response.

Keep the CLI-generated mount policy. It explicitly selects which Harness
targets are reachable through the service.

```ts title="src/service/support/v1/harness/supportHarnessMount.ts" write
import { supportHarness } from '../../../../harness/support/supportHarness.js'

export { supportHarness }

export const supportHarnessPolicy = {
	publish: { agents: ['classify_support_message'], workflows: [] },
	targets: { agents: {}, workflows: {} },
} as const
```

The service adds the command definition and mounts the Harness once.

```ts title="src/service/support/v1/supportV1Service.ts" write
import { classifySupportMessageCommandBuilder } from './command/classifySupportMessage/classifySupportMessageCommandBuilder.js'
import { supportHarness, supportHarnessPolicy } from './harness/supportHarnessMount.js'
import { supportV1ServiceBuilder } from './supportV1ServiceBuilder.js'

export const supportV1Service = supportV1ServiceBuilder
	.addCommandDefinition(classifySupportMessageCommandBuilder.getDefinition())
	.mountHarness(supportHarness, supportHarnessPolicy)
```

The command has no HTTP metadata yet. Adding an HTTP endpoint later does not
change how the command invokes the agent, and the endpoint will remain
protected unless its builder explicitly calls `makeEndpointPublic()`.
