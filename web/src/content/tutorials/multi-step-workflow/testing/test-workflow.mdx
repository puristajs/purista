Test the native Harness definition first. Use separate strict fake providers
and a temporary `localDurableExecution` bundle. Make the first two planning
calls reject with a retriable `ModelError`. The first workflow run performs
classification once and makes two planning attempts because of the bounded
step retry policy.

```ts title="src/harness/support/supportResolutionWorkflow.test.ts"
await expect(
	firstSession.workflows.resolve_support_case.run(input, { durable: { runId: 'support-run-1' } }),
).rejects.toBeDefined()
expect(classificationProvider.requests).toHaveLength(1)
expect(resolutionObject).toHaveBeenCalledTimes(2)
```

Shut down the first Harness runtime and create a new local durable bundle from
the same directory. Then queue a planning response and invoke the same native
workflow run again. Harness restores the session and workspace lifecycle,
loads `classify-case-v1` from its committed checkpoint, and runs only the
unfinished planning step.

```ts title="src/harness/support/supportResolutionWorkflow.test.ts"
resolutionProvider.enqueueObject({
	object: { summary: 'Verify the caller and secure the card.', nextAction: 'freeze_card' },
	usage,
	finishReason: 'stop',
})

await expect(
	secondSession.workflows.resolve_support_case.run(input, { durable: { runId: 'support-run-1' } }),
).resolves.toMatchObject({
	status: 'completed',
	output: { caseId: 'case-1', classification: { category: 'card', urgency: 'urgent' } },
})
expect(classificationProvider.requests).toHaveLength(1)
expect(resolutionObject).toHaveBeenCalledTimes(3)
```

Next, test the command with `createCommandContextMock`. Inject the policy
resource, set trusted tenant and principal ids on the message, resolve only the
declared workflow stub, and assert the exact session and run ids. This test is
fast and explains the command boundary without starting a service.

Finally, start the mounted service on `DefaultEventBridge`. The integration
suite proves that changed input cannot reuse the same durable run, invalid
structured model output is not retried, and a direct workflow caller denied by
the mounted business guard is rejected before either model runs.

```bash title="Verify the multi-step workflow chapter" replay="project"
npm run build
npm test
npm run lint
npm run demo
```

The retained tests and demo pass without an API key. The demo invokes the
PURISTA command through a real EventBridge with strict fake providers. This
chapter remains a draft until the released PURISTA v4 and Harness v3 packages
pass a clean registry replay.
