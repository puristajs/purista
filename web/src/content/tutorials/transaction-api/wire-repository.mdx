---
title: Declare and inject the storage resource
description: Connect the repository type to the service builder and the repository instance to application startup.
order: 24
---

PURISTA calls application-owned dependencies **resources**. A service declares
which resources its handlers need. Startup supplies the actual objects.

That separates the business operation from the storage choice. The command
will ask its resource to record a transaction; it will not construct a database
client or repository on each request.

## Declare the requirement

Replace `src/service/banking/v1/bankingV1ServiceBuilder.ts`:

```ts title="src/service/banking/v1/bankingV1ServiceBuilder.ts"
import { ServiceBuilder, type ServiceInfoType } from '@purista/core'
import type { TransactionRepository } from '../../../transactionRepository.js'
import { generalBankingServiceInfo } from '../generalBankingServiceInfo.js'
import { bankingServiceV1ConfigSchema } from './bankingServiceConfig.js'

export const bankingServiceInfo = {
	serviceVersion: '1',
	...generalBankingServiceInfo,
} as const satisfies ServiceInfoType

export const bankingV1ServiceBuilder = new ServiceBuilder(bankingServiceInfo)
	.setConfigSchema(bankingServiceV1ConfigSchema)
	.defineResource<'transactions', TransactionRepository>()
```

The metadata and configuration schema are still the generated ones.
`defineResource<'transactions', TransactionRepository>()` adds one named
resource requirement. The first type argument is the name handlers will use;
the second describes the object's methods.

This declaration does not create storage. It gives the builder enough
information to type `context.resources.transactions` in later commands.

## Supply the instance at startup

Replace `src/index.ts`:

```ts title="src/index.ts"
import { gracefulShutdown, initLogger } from '@purista/core'
import { getEventBridge } from './eventbridge.js'
import { startHttpServer } from './http.js'
import { bankingV1Service } from './service/banking/v1/bankingV1Service.js'
import { TransactionRepository } from './transactionRepository.js'

async function main() {
	const logger = initLogger()
	const eventBridge = await getEventBridge(logger)
	const banking = await bankingV1Service.getInstance(eventBridge, {
		logger,
		resources: { transactions: new TransactionRepository() },
	})
	await banking.start()

	const { honoService, closeSocket } = await startHttpServer({
		eventBridge,
		logger,
		services: [banking],
	})

	gracefulShutdown(logger, [honoService.prepareDestroy(), eventBridge, banking, closeSocket, honoService])
	logger.info('Example Bank is listening on http://127.0.0.1:3000')
}

main().catch(error => {
	process.stderr.write(`${error}\n`)
	process.exit(1)
})
```

The new import makes the repository class available. The new `resources`
option supplies **one instance** when Banking is created. All commands in
that service instance will use it.

Hono still receives the same Banking instance, and both still use the same
EventBridge. No HTTP configuration or manually written route is needed here.

You can start `npm run dev` and check that `GET /api/v1/bank` still returns
`200`. The bank information command does not use the repository, but its
service now has that dependency.

The existing HTTP test also creates Banking directly. It must supply the new
resource too. Stop the server and [update the test setup next](/tutorials/transaction-api/test-resource-wiring/).
