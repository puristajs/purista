---
title: Run the API
description: Start the local service, create a local fixture session, and inspect its seeded transaction history.
order: 21
---

Start the application from the `purista` repository root:

```bash title="Start the banking API"
npm run dev -w @purista/banking-tutorials
```

The seed data contains one credit transaction on `account-a`. First create a
local fixture session as Alice. `-c` writes the opaque cookie to the named
cookie jar:

```bash title="Create Alice's local tutorial session"
curl --fail -c .tutorial-cookie -X POST http://127.0.0.1:3010/auth/login \
  -H 'content-type: application/json' \
  --data '{"actor":"alice"}'
```

Then send that cookie with the protected request:

```bash title="Read Alice's synthetic account history"
curl --fail \
  -b .tutorial-cookie \
  http://127.0.0.1:3010/api/v1/accounts/account-a/transactions
```

The response contains `accountId: "account-a"` and
`transaction-seed-a-1`. Amounts are stored as integer minor units: `4250`
means EUR 42.50. Storing a whole number avoids binary floating-point rounding
in the command contract.

The local login accepts a documented synthetic person. `alice` and `bob` may
read account A, `carol` may read account C, and `dana` is the operations person
for posting to account A. The protected API takes identity from the
server-side session, not from the URL or JSON payload.

## Test the starting result

Replace the cookie jar with a Bob session, then try Bob against Carol's
account:

```bash title="Create Bob's local tutorial session"
curl --fail -c .tutorial-cookie -X POST http://127.0.0.1:3010/auth/login \
  -H 'content-type: application/json' \
  --data '{"actor":"bob"}'
```

```bash title="Prove that a signed-in person still has limited access"
curl -i -b .tutorial-cookie \
  http://127.0.0.1:3010/api/v1/accounts/account-c/transactions
```

Expect `403`. This is a business permission denial, not a failed login. Stop
and restart the process whenever you need the seed state again.
