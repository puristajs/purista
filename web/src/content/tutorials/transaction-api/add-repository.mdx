title: Implement the transaction repository
description: Write the storage object that records transactions, rejects duplicates, and returns account history.
order: 23
---

The schemas describe records, but something must keep them between requests.
A **repository** is an application object that owns storage operations.
Start with a small in-memory implementation so we can focus on PURISTA wiring.

Create `src/transactionRepository.ts`:

```ts title="src/transactionRepository.ts"
import { randomUUID } from 'node:crypto'
import { HandledError, StatusCode } from '@purista/core'
import type { RecordedTransaction, TransactionInput } from './transaction.js'

/** Process-local storage. Each new instance starts empty. */
export class TransactionRepository {
	private readonly transactions = new Map<string, RecordedTransaction>()

	/** Reject a duplicate source record instead of storing it twice. */
	record(input: TransactionInput): RecordedTransaction {
		const key = `${input.accountId}:${input.sourceTransactionId}`
		if (this.transactions.has(key)) {
			throw new HandledError(StatusCode.Conflict, 'This source transaction is already recorded')
		}
		const transaction = { ...input, transactionId: randomUUID() }
		this.transactions.set(key, transaction)
		return { ...transaction }
	}

	/** Return copies so callers cannot change stored records by modifying a response. */
	list(accountId: TransactionInput['accountId']): RecordedTransaction[] {
		return [...this.transactions.values()]
			.filter(transaction => transaction.accountId === accountId)
			.map(transaction => ({ ...transaction }))
	}
}
```

A `Map` stores each record under an account/source reference pair.
`record` checks that key before writing, adds a UUID, saves the result, and
returns a copy. `list` selects records for one account and returns copies,
so callers cannot modify storage by changing the returned objects.

The duplicate rule is deliberate: repeating a source reference for the same
account returns a conflict. It does not create a second record or silently
change the first. This is a rejection policy, not a replay mechanism that
returns an earlier successful response.

`HandledError` tells PURISTA that a known condition prevented the operation.
`StatusCode.Conflict` will become HTTP `409` at the command's HTTP boundary.
An unexpected exception would instead be an internal failure.

Run `npm run build`. The server still behaves as before because nothing uses
this repository yet. Do **not** instantiate it inside each command handler:
a new instance on every request would lose the preceding request's data.

This repository is not a production database. It loses data on restart and
is not shared by separate processes. A database implementation would need its
own uniqueness constraint and transaction rules.
