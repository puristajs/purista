The Hono protection middleware is configured in
`examples/banking/src/index.ts`:

```ts title="examples/banking/src/index.ts"
hono.setProtectMiddleware(async function (context, next) {
  const session = findSession(context.req.header('cookie'))
  if (!session) {
    return context.json({ title: 'A local session is required' }, 401)
  }
  context.set('principalId', session.principalId)
  context.set('tenantId', session.tenantId)
  return next()
})
```

Hono runs this middleware for endpoints whose HTTP security is enabled. The
command definitions use the default protected status. The middleware then puts
`principalId` and `tenantId` in the request context that the command guard
receives.

The important boundary is where the values come from. In this local example,
they come from a server-side session record addressed by an opaque HttpOnly
cookie. The fixture login still accepts a synthetic name without a credential,
so it is not production authentication. A production middleware must derive
these values from a verified credential and must never copy them from a JSON
payload or an unverified client value.

## Test a forged payload cannot choose the actor

The transaction schema has no `principalId` or `tenantId` fields. Even if a
transport ignores an unknown JSON field, the guard reads the person from the
session-aware middleware, not an identity value in the payload. The safe rule
is: domain payloads describe a transaction, not the caller.

for the supported Hono protection model.
