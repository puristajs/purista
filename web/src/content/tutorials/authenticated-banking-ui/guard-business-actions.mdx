title: Check account permissions with guards
description: "Use before guards for the concrete decision: may this actor perform this action on this account?"
order: 34
---

The two guards in `examples/banking/src/service.ts` have different jobs.
`requireReadableAccount` checks the requested account against the actor's read
mandate. `requirePostingAccess` checks whether the actor may record a posting
for the payload's account.

```ts title="examples/banking/src/service.ts"
.setBeforeGuardHooks({
  accountRead: async function (context, _payload, parameter) {
    await requireReadableAccount(context, { accountId: parameter.accountId })
  },
})
```

The guard runs after the command's parameter and payload schemas validate, and
before the handler calls the repository. It receives the trusted principal from
the command context and the validated account ID. That is why Bob can read A
but cannot read C, and why Bob cannot post to A despite holding a valid local
fixture session.

Named guards in one stage run concurrently. Do not use two hook names as an
ordered pipeline or let one mutate state for the other. If a permission or
account state can change during a write, the handler and repository need an
atomic recheck as well; a before guard is not a transaction lock.

## Test that denial has no effect

Send the posting request from the previous chapter with Bob's cookie jar, then
list account A with Alice's cookie jar. The `sourceTransactionId` must not be
in the list. This proves both the `403` response and the missing repository
write.
