RAG means retrieval augmented generation. The application first stores a source as searchable chunks. Later, a model can choose a retrieval tool and answer from the matching chunks.

This chapter teaches the PURISTA boundaries that make that path reviewable:

```text title="Service owned RAG path"
Identity StateStore -> opaque session -> ProtectMiddleware
Knowledge command -> guard -> Knowledge service resource
runIngestKnowledge -> ingestKnowledge workflow -> embeddings -> pgvector
answerKnowledgeQuestion agent -> searchKnowledge host tool -> retrieveKnowledge workflow
  -> queryKnowledgeRepository -> tenant scoped matches
runAnswerKnowledgeQuestion / streamAnswerKnowledgeQuestion -> Hono
```

The Example Bank contributes one small help document. The framework concepts are the important part: schemas describe data, resources own external state, guards authorize business actions, and address first calls cross service boundaries through EventBridge.

The required path is CLI first. Start with a published PURISTA project, replace the generated placeholders with the service owned source, run each focused check, and finish at the composed HTTP application. The optional React pages remain separate from this backend path.
