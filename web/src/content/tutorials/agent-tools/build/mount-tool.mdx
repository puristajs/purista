The native Harness definition knows the tool contract. The Support mount now
supplies its PURISTA implementation. This is the adapter layer between the two
libraries:

```text title="Portable definition and PURISTA binding"
Harness module                      Support service mount
-------------------------------     --------------------------------
lookup_transaction contract    ->   typed host-tool implementation
answer_transaction_question    ->   published EventBridge target
model alias primary            ->   runtime binding on a later page
```

## Define the Support authorization policy

First define the business policy used to publish the agent itself.

```ts title="src/service/support/v1/SupportResources.ts" write
export interface SupportQuestionPolicy {
	canAsk(
		input: Readonly<{
			tenantId: string
			principalId: string
			accountId: string
			transactionId: string
		}>,
	): Promise<boolean>
}
```
Declare that resource on the generated Support service builder. The concrete
policy will be injected when the service instance is created.

```ts title="src/service/support/v1/supportV1ServiceBuilder.ts" write
import { ServiceBuilder } from '@purista/core'
import type { SupportQuestionPolicy } from './SupportResources.js'

export const supportV1ServiceBuilder = new ServiceBuilder({
	serviceName: 'Support',
	serviceVersion: '1',
	serviceDescription: 'Owns support conversations and support automation',
}).defineResource<'supportQuestionPolicy', SupportQuestionPolicy>()
```
## Share one business rule across both entry points

Create one helper for the outer command and the directly published agent. Its
policy input names the account and transaction being requested. The session
helper combines the question with trusted caller identity, then hashes the
value so raw identities do not become storage keys.

```ts title="src/service/support/v1/requireSupportQuestion.ts" write
import { createHash } from 'node:crypto'
import { HandledError, StatusCode } from '@purista/core'
import type { SupportQuestionPolicy } from './SupportResources.js'

export async function requireSupportQuestion(
	policy: SupportQuestionPolicy,
	input: Readonly<{
		tenantId?: string
		principalId?: string
		accountId: string
		transactionId: string
	}>,
) {
	if (!input.tenantId || !input.principalId)
		throw new HandledError(StatusCode.Unauthorized, 'A valid session is required')
	if (
		!(await policy.canAsk({
			tenantId: input.tenantId,
			principalId: input.principalId,
			accountId: input.accountId,
			transactionId: input.transactionId,
		}))
	) {
		throw new HandledError(StatusCode.Forbidden, 'This transaction question is not allowed')
	}
}

export function supportQuestionSessionId(
	identity: Readonly<{ tenantId?: string; principalId?: string }>,
	questionId: string,
) {
	if (!identity.tenantId || !identity.principalId)
		throw new HandledError(StatusCode.Unauthorized, 'A valid session is required')
	const digest = createHash('sha256')
		.update(`${identity.tenantId}:${identity.principalId}:${questionId}:support-question-v1`)
		.digest('hex')
	return `support-question:${digest}`
}
```
## Implement the mount adapter

Replace the generated mount file with the complete binding and mount policy.

```ts title="src/service/support/v1/harness/supportHarnessMount.ts" write
import type { HarnessBusinessGuardContext } from '@purista/core'
import { supportHarness } from '../../../../harness/support/supportHarness.js'
import {
	getTransactionSummaryOutputSchema,
	getTransactionSummaryParameterSchema,
	getTransactionSummaryPayloadSchema,
} from '../../../transaction/v1/command/getTransactionSummary/schema.js'
import { requireSupportQuestion } from '../requireSupportQuestion.js'
import type { SupportQuestionPolicy } from '../SupportResources.js'
import { supportV1ServiceBuilder } from '../supportV1ServiceBuilder.js'

export { supportHarness }

const lookupTransactionTool = supportV1ServiceBuilder
	.getHarnessHostToolBuilder(supportHarness.catalog.hostTools.lookup_transaction)
	.canInvoke(
		'Transaction',
		'1',
		'getTransactionSummary',
		getTransactionSummaryOutputSchema,
		getTransactionSummaryPayloadSchema,
		getTransactionSummaryParameterSchema,
	)
	.setHandler(async (context, input) => {
		const { tenantId: _tenantId, ...summary } = await context.service.Transaction['1'].getTransactionSummary(input, {})
		return summary
	})
	.getDefinition()

export const supportHarnessPolicy = {
	publish: { agents: ['answer_transaction_question'], workflows: [] },
	hostTools: { lookup_transaction: lookupTransactionTool },
	targets: {
		agents: {
			answer_transaction_question: {
				beforeGuards: {
					mayUseSupportAgent: async (
						context: HarnessBusinessGuardContext<{ supportQuestionPolicy: SupportQuestionPolicy }>,
						input: { accountId: string; transactionId: string },
					) => {
						await requireSupportQuestion(context.resources.supportQuestionPolicy, {
							...context.identity,
							accountId: input.accountId,
							transactionId: input.transactionId,
						})
					},
				},
			},
		},
		workflows: {},
	},
} as const
```
`.canInvoke(...)` is the capability declaration. It gives this tool handler a
typed `context.service.Transaction['1'].getTransactionSummary(...)` function.
That call goes through EventBridge and carries the current trace, correlation,
tenant, and principal values. The handler does not accept identity from the
model input.

The handler removes `tenantId` from the command result because that field is
needed for server-side scope validation but is not part of the model-facing
tool output contract. Harness validates the returned object against
`transactionSummarySchema` before it is sent back to the model.

The published agent has its own business guard because callers can address a
mounted target directly. The outer Support command uses the same policy before
it invokes the agent. The Transaction command keeps its separate account
guard because every caller of that data capability must pass the same rule.

For a tool that only forwards one command without changing input or output,
`commandAsHarnessTool(...)` is a shorter adapter. The builder used here is
appropriate because the tool removes the internal `tenantId` field from the
model-visible result. The same builder can explicitly declare streams, queue
jobs, agents, workflows, and emitted events when a tool really needs them.

Run a typecheck. This proves the host-tool input/output contracts match the
command call and the published agent guard can access the declared resource.

```bash title="Verify the mounted tool binding" replay="project"
npm run build
```
