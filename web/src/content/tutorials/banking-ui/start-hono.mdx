title: Read the generated Hono HTTP server
description: Extend the generated Hono composition so it can serve browser files and later register PURISTA services.
order: 12
---

Hono receives HTTP requests. PURISTA owns the services that perform business
work. The generator already put both responsibilities in one composition root,
using the in-process `DefaultEventBridge`.

Open generated `src/http.ts`. Its order matters:

```ts title="src/http.ts"
const honoService = await honoV1Service.getInstance(input.eventBridge, {
  logger: input.logger,
  serviceConfig: { ...httpConfig.serviceConfig, services: input.services },
})
await honoService.start()
const serverInstance = serve({ fetch: honoService.app.fetch, port: httpConfig.port })
```

`src/index.ts` starts the EventBridge first, creates generated services, and
passes them as `input.services`. Hono then registers the endpoints those
services declare. This is local registration, not remote service discovery.

`@hono/node-server` supplies the Node listener. The generated configuration
uses port 3000 and enables the Hono health endpoint. A listener accepting
connections is still not a full production readiness claim.

```bash title="Request the generated Hono health endpoint"
npm run dev
# In another terminal:
curl -i http://127.0.0.1:3000/health
```

Expect `200`. A connection refusal means the foreground process is not running
or the selected port differs.
