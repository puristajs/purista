The CLI has created the agent folder and added its definition to the service.
Open the generated builder, replace its starter schemas with a small scoped
support request, and expose the aggregate endpoint:

```ts title="Generated agent builder after its first edit"
.addPayloadSchema(z.object({ accountId: accountIdSchema, text: z.string().min(1).max(2_000) }))
.addOutputSchema(z.object({ answer: z.string().min(1).max(500) }))
.exposeAsHttpEndpoint('POST', 'customer-support/guarded-answer', { streamingMode: 'aggregate' })
```

The test starts `bankingGuardedAssistant`, a normal PURISTA service. Its
generated endpoint is `POST /api/v1/customer-support/guarded-answer`. The
test uses an opaque server-side identity like the other banking checkpoints;
the browser does not supply a principal or tenant header.

Four controls answer four different questions:

| Control | Question | Example |
| --- | --- | --- |
| Hono protection | Who made this request? | The local session identifies Bob. |
| Business guard | May that person read this account? | Bob may read A, not C. |
| Agent capability | Which tool may the agent use? | It may use only `read`. |
| Content interceptor | May this text cross this boundary? | A synthetic marker stops the run. |

Keeping these questions separate matters. A helpful model prompt is not a
business guard, and an input check is not a substitute for an account scope.

```bash title="Run the generated and completed boundary test"
npx vitest run examples/banking/src/ai/guarded-assistant.test.ts
```
