---
title: Understand the external API boundary
description: Keep the implemented inbound legacy endpoint distinct from an outbound call to a bank API that this checkpoint does not yet provide.
order: 45
---

The current example accepts a legacy request at
`POST /api/v1/legacy/transactions`. That is an **inbound** HTTP boundary: a
client calls the banking service.

It does not call a legacy bank API. There is no `legacyBank` resource, HTTP
client, Docker Compose file, mock server, timeout setting, or malformed-response
fixture in `examples/banking` today. Do not add a `fetch` call to a command and
then claim it has a verified integration contract.

An outbound integration needs its own resource at the composition root, a
specific request and response schema, timeout and error handling, and a mock
that can exercise success, malformed data, duplicate delivery, and timeout.
It must pass the normalized result to the same guarded domain operation. That
work is intentionally outside this current local checkpoint.

## Test the available boundary

Use the inbound endpoint with the documented JSON body and run:

```bash title="Run the implemented transform integration test"
npm run test -w @purista/banking-tutorials
```

This proves the local Hono-to-command transform path. It does not prove an
external network round trip or retry behavior.
