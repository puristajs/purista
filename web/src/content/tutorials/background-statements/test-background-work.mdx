Test this feature in layers. Each test answers one question, so a failure
points to the contract or component that needs attention.

| Test | What it proves | What it does not prove |
| --- | --- | --- |
| Generated queue definition test | The queue's name and schemas resolve | A job was delivered |
| Command-context test | An authorized command enqueues the typed job and returns its reference | A worker ran |
| Queue-worker context test | The worker checks current account access, writes metadata, and acknowledges success | A bridge retried or persisted it |
| Service startup test | Queue and worker definitions start with the selected local bridges | HTTP-to-worker timing or recovery |

## Run the focused tests while building

```bash title="Run the queue, command, and worker tests"
npm test -- --run src/service/bankingOperations/v1/queue/generateStatement/generateStatementQueueBuilder.test.ts
npm test -- --run src/service/bankingOperations/v1/command/requestStatementGeneration/requestStatementGenerationCommandBuilder.test.ts
npm test -- --run src/service/bankingOperations/v1/queue-worker/generateStatementWorker/generateStatementWorkerQueueWorkerBuilder.test.ts
```

Then run the whole application suite before you use the chapter as a completed
checkpoint:

```bash title="Verify the finished banking checkpoint"
npm run typecheck -w @purista/banking-tutorials
npm run test -w @purista/banking-tutorials
```

The checked-in reference uses an equivalent direct worker test in
`examples/banking/src/advanced/service.test.ts`. It creates a
`createQueueWorkerContextMock(generateStatementWorker, ...)`, calls the
registered handler, and asserts one completion plus one metadata record. The
same file uses a command-context mock to prove that
`requestStatementGeneration` returns the queue reference.

Add a real queue-adapter integration test only when the application owns a
durable adapter and persisted projection. That test should cover the full
enqueue-to-worker path, an access denial after enqueue, duplicate delivery,
retry, and restart recovery. Do not use this in-memory tutorial checkpoint as
evidence for those production behaviors.
