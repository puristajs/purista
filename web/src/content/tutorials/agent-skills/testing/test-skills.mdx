The Skill definition test from the binding page checks the colocated manifest
and confirms that this Skill declares no logical executable runtime.

Add a focused agent test. It proves the agent owns direct definition references
for the Skill and the read tool. No write, shell, or network capability appears
in the graph.

```ts title="src/service/support/v1/harness/agent/answerProcedureQuestion/answerProcedureQuestionAgent.test.ts" write
import { builtInTools } from '@purista/harness'
import { describe, expect, it } from 'vitest'
import { supportMethodsSkill } from '../../skill/support-methods/supportMethodsSkill.js'
import { answerProcedureQuestionAgent } from './answerProcedureQuestionAgent.js'

describe('answerProcedureQuestionAgent', () => {
	it('uses direct Skill and read-tool definitions', () => {
		expect(answerProcedureQuestionAgent.id).toBe('answerProcedureQuestion')
		expect(answerProcedureQuestionAgent.skills).toEqual([supportMethodsSkill])
		expect(answerProcedureQuestionAgent.tools).toEqual([builtInTools.read])
		expect(Object.isFrozen(answerProcedureQuestionAgent)).toBe(true)
	})
})
```


Run both definition tests. They need no model credentials or EventBridge.

```bash title="Run the Skill definition tests" replay="project"
npm test -- src/service/support/v1/harness/skill/support-methods/supportMethodsSkill.test.ts src/service/support/v1/harness/agent/answerProcedureQuestion/answerProcedureQuestionAgent.test.ts
```

These tests cover the static capability boundary. The next page starts the
mounted service and proves that the model reads the Skill lazily.
