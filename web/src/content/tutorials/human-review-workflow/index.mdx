This chapter teaches a durable application review. A PURISTA command starts a
native Harness workflow. The workflow reaches an external wait, and the
command returns an ordinary `waiting` result. A later command records an
authorized decision, signals the wait, and resumes the same run.

The Example Bank fixture asks a reviewer to approve or reject one card freeze.
The banking rule stays small so the Framework boundaries remain visible.

```text title="Human review execution path"
request command
  -> business guard
  -> EventBridge workflow address
  -> durable external wait
  -> typed waiting response

decision command
  -> reviewer guard
  -> atomic decision record
  -> signal wait and resume the same run
  -> approved Transaction command, once
```

Harness storage owns run checkpoints and the opaque wait. The Support service's
database resource owns review records and reviewer decisions. The Transaction
service owns the business effect. PURISTA StateStore is not used for any of
these durable business records.

An external wait is different from model tool approval. Use a Harness approval
interrupt when a person must approve one model-selected tool call; AI SDK UI
Message Stream v1 can then carry the standard approval parts. This chapter
teaches an application workflow whose client contract is the typed states
`waiting`, `approved`, `rejected`, `expired`, and `cancelled`.
