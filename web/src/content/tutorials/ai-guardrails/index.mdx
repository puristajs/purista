This chapter adds content guardrails to one structured Harness agent. An input
rail blocks a small instruction-override pattern before the provider runs. An
output rail removes card-like digit sequences before the result leaves Harness.

```text title="Guarded classification path"
authenticated PURISTA caller
  -> PURISTA business authorization guard
  -> mounted Harness agent target
  -> Harness input rail
  -> model provider
  -> Harness output rail
  -> validated command result
```

These checks have different jobs. PURISTA guards decide whether a trusted
caller may use a business capability. Harness guardrails inspect or transform
content around model and tool work. A content rule must not grant business
access, and an authorization check must not be presented as model safety.

The example uses a short support-message fixture. Its reusable lesson is how to
attach provider-neutral rails to a direct agent definition, mount that agent on
a service, and test every boundary without credentials.
