# Streaming v1 Production Spec (Internal Draft)

This document is intended to be implementation-ready. It aligns streaming with existing Purista patterns (commands, subscriptions, EventBridge, ServiceBuilder) while prioritizing strong typing and production-grade stability.

## Goals

- Provide a first-class streaming primitive that is "command-like" (payload + params + guards + HTTP exposure).
- Allow commands/subscriptions/streams to *consume* remote streams with invoke-like DX and strong typing.
- Support HTTP exposure as SSE (`text/event-stream`) with good DX for browsers and server-to-server clients.
- Work across all event bridge integrations without cross-instance stream mixups.
- Provide cancellation, timeouts, and robust error handling.
- Ship implementation-grade documentation, examples, and API inline docs for IDE/autocomplete.
- Meet a minimum test coverage target of `>= 80%` for streaming-related modules.

## Non-goals (v1)

- Exactly-once chunk delivery.
- Transparent resumability across process/broker restarts.
- Auto-broadcasting each chunk as a business event (1:N chunk consumption) by default.
- Full duplex streaming input (client -> server data stream). Control messages are allowed (cancel/heartbeat).

## Core concepts

- A *stream* is an invocation that produces multiple response frames (chunks) and ends with `complete` or `error`.
- A *stream session* is uniquely identified by `sessionId` (string, generated by caller).
- The *owner instance* is the service instance that accepted the stream open request and is responsible for producing frames.

## Public API surface (proposed)

### 1) ServiceBuilder additions

Mirror existing patterns:

- `getStreamBuilder(name, description, finalEventName?)` -> `StreamDefinitionBuilder`
- `addStreamDefinition(...streams)` -> store definitions similarly to commands/subscriptions
- `getStreamDefinitions()` -> available after `resolveDefinitions()`
- `resolveDefinitions()` returns `{ commands, subscriptions, streams }`

### 2) StreamDefinitionBuilder (command-like)

Naming and style must mirror `CommandDefinitionBuilder`:

- `addPayloadSchema(schema, contentType?, contentEncoding?)`
- `addParameterSchema(schema)`
- `addChunkSchema(schema, validateChunks = true)`
- `addFinalSchema(schema)` (optional)
- `setFinalEventName(name)` (optional; makes final aggregate subscribable)
- `enableChunkAggregation(enabled = true)`
- `setFinalAggregation(initial, reduce, finalSchema?)` (optional; overrides default aggregation)
- `exposeAsHttpStreamEndpoint(method, path, contentTypeRequest?, contentEncodingRequest?)`
- HTTP security + OpenAPI metadata methods similar to commands:
  - `makeEndpointPublic()`, `enableHttpSecurity()`, `setOpenApiSummary()`, `setOpenApiOperationId()`, `addOpenApiTag()`, `addErrorStatusCode()`, `addQueryParameter(...)`
- `canInvoke(...)` and `canEmit(...)` same as command/subscription builder.
- `canConsumeStream(...)` declares typed `context.stream.*` open/consume functions (see below).
- `setStreamFunction(fn)` required (non-arrow function).

OpenAPI parity requirement:
- StreamBuilder must store enough metadata to generate OpenAPI similarly to commands:
  - `inputPayload` schema
  - `parameter` schema
  - `chunk` schema
  - optional `final` schema
  - response content type `text/event-stream`

#### Stream function signature (producer side)

Keep async/await style and avoid callback wording:

```ts
async function (
  context: StreamFunctionContext<...>,
  payload: Payload,
  parameter: Parameter,
  writer: StreamWriter<Chunk, Final>,
) : Promise<void>
```

Notes:
- `writer.write()` returns a Promise. Backpressure semantics depend on transport.
- `writer.close(final?)` ends the stream.
- `writer.fail(err)` ends the stream with an error frame.
- `writer.onCancel(cb)` informs the handler about cancellation (HTTP disconnect or cancel control frame).

### 3) Context additions (invoke-like consumption)

Current state:
- command/subscription contexts expose request-response invocations via `context.service` (typed by `canInvoke`).

Add:
- `context.stream` for consuming streams (typed by `canConsumeStream`).

DX target:

```ts
const handle = await context.stream.UserService['1'].searchUsers(payload, params)
for await (const frame of handle) {
  // frame.payload typed as Chunk
}
await handle.cancel()
```

Implementation pattern:
- introduce a `StreamInvokeList` similar to `InvokeList` (but with chunk/final schemas).
- reuse `createInvokeFunctionProxy` to build the nested proxy for `context.stream`.
- implement `Service.getConsumeStreamFunction(...)` similar to `Service.getInvokeFunction(...)`:
  - validate payload/params against schemas from `canConsumeStream`
  - open the stream via `eventBridge.openStream(...)`
  - validate incoming chunks/final frames against chunk/final schemas unless disabled

### 4) EventBridge interface additions

We need explicit streaming primitives on the EventBridge to avoid bridge-specific hacks in services.

Proposed additions to `EventBridge`:

- `openStream(input, opts?) => Promise<StreamHandle<Chunk>>`
- `registerStream(address, cbOpen, metadata, eventBridgeConfig) => Promise<string>`
- `unregisterStream(address) => Promise<void>`

Additionally, each bridge must implement per-instance control message receiving for cancellations:
- a per-instance control subscription (not shared) keyed by `receiver.instanceId`
- dispatch control frames to the correct running stream session by `sessionId`

## Message protocol (proposed)

### Add new message type

Add `EBMessageType.Stream = 'stream'`.

Rationale:
- avoids overloading `CustomMessage` and accidentally matching business subscriptions
- keeps routing separate and explicit
- allows bridges to implement optimized topics/queues for stream traffic

### Stream open request

```ts
type StreamOpenRequest<Payload, Params> = {
  messageType: EBMessageType.Stream
  correlationId: CorrelationId // used as sessionId (string) for v1
  receiver: EBMessageAddress   // target stream: serviceName/serviceVersion/serviceTarget(streamName)
  payload: { payload: Payload; parameter: Params }
} & EBMessageBase
```

Rules:
- `correlationId` is required and acts as `sessionId`.
- `sender.instanceId` is the caller instance.
- open requests are delivered to one service instance (shared load-balancing).

### Stream frames (producer -> consumer)

```ts
type StreamFrame<Chunk, Final> = {
  messageType: EBMessageType.Stream
  correlationId: CorrelationId // sessionId
  receiver: EBMessageSenderAddress // original caller (includes instanceId)
  payload: {
    frameType: 'start' | 'chunk' | 'complete' | 'error' | 'heartbeat'
    sequence: number
    chunk?: Chunk
    final?: Final
    error?: { status: StatusCode; message: string; isHandledError: boolean; data?: unknown; traceId?: string }
  }
} & EBMessageBase
```

Rules:
- frames MUST be addressed to the original caller (`receiver = original.sender`).
- `sender` MUST include the owner instance id (the stream producer).
- `sequence` starts at 0 for `start` and increments for each frame.

### Stream control (consumer -> producer)

```ts
type StreamControl = {
  messageType: EBMessageType.Stream
  correlationId: CorrelationId // sessionId
  receiver: EBMessageAddress & Required<Pick<EBMessageAddress, 'instanceId'>> // owner instance
  payload: { frameType: 'cancel'; reason?: string }
} & EBMessageBase
```

Routing requirement:
- control frames MUST be delivered to the owner instance (no load-balancing).
- bridges must implement a per-instance control subscription keyed by `receiver.instanceId`.

## Service runtime behavior (normative)

On open request:
- validate payload/params using StreamDefinition schemas (same behavior as commands)
- run before-guard hooks (same semantics as commands)
- send `start` frame immediately after successful validation/guards
- run the stream function, providing `StreamWriter`

On `stream.write(chunk)`:
- if `validateChunks = true`, validate chunk against `chunkSchema` before publishing
- publish a `chunk` frame with next `sequence`

On `stream.close(final?)`:
- if aggregation is enabled:
  - compute aggregate (default or custom reducer)
  - if `finalSchema` exists, validate aggregate once
  - publish `complete` frame with `final`
- else:
  - publish `complete` frame with no `final`
- if `finalEventName` is configured:
  - emit a `CustomMessage` with `eventName = finalEventName` and payload = final aggregate
  - this makes the result subscribable by existing subscriptions

On error:
- map thrown errors into `HandledError`/`UnhandledError`-shaped payload
- publish `error` frame and then terminate the session

On cancel:
- stop producing as soon as possible
- publish a terminal `cancel` frame (no `StatusCode`) and then stop (no extra `complete` frame)
- always cleanup session resources

On shutdown:
- stop accepting new stream open requests
- cancel/close active sessions with a consistent error/cancel signal

## Consumer runtime behavior (normative)

`EventBridge.openStream(...)`:
- generates a new `sessionId` (correlationId)
- sends a StreamOpenRequest
- registers the session in an in-memory map keyed by sessionId
- yields frames via `StreamHandle[Symbol.asyncIterator]`
- supports `cancel()` by publishing a StreamControl(cancel) addressed to the owner instance (once known)

Chunk/final validation on consumer:
- if the consuming site declared `canConsumeStream(..., chunkSchema, finalSchema?)`, validate received frames accordingly (similar to `canInvoke` output schema validation).
- allow disabling consumer-side validation explicitly for performance (default ON in v1).

## HTTP/SSE projection (normative)

When exposing a stream as HTTP:
- response content type MUST be `text/event-stream`
- SSE events MUST encode frames as JSON in `data:`
- recommended SSE event names:
  - `start`, `chunk`, `complete`, `error`, `heartbeat`
- recommended `id:` is `sequence` (for possible resume semantics later)

OpenAPI generation requirements (to match current Purista behavior):
- Stream HTTP exposure metadata MUST provide a `openApi` object equivalent to command exposure:
  - `summary`, `description`, `tags`, `operationId`, `isSecure`, `additionalStatusCodes`, `query`
- Stream HTTP exposure metadata MUST provide:
  - `inputPayload` schema (when method is not GET)
  - `parameter` schema (path/query parameters)
  - `chunk` schema and optional `final` schema (for documentation)
- OpenAPI response:
  - `200` response content type MUST be `text/event-stream`
  - response schema SHOULD describe the JSON frame shape (frameType + sequence + chunk/final/error)
  - handshake failures (auth/validation) SHOULD be modeled as normal JSON error responses (401/400/etc.)

Method support:
- `GET`: query params only (EventSource compatible)
- `POST`: payload + params (fetch streaming client)

Security:
- reuse existing HTTP security toggles from command exposure.

Error handling:
- handshake errors (auth, validation) SHOULD be returned as normal HTTP error responses before SSE begins.
- mid-stream errors MUST be sent as SSE `error` event then close connection.

OpenAPI method nuance:
- For `GET` SSE endpoints, OpenAPI `requestBody` MUST be omitted (current OpenAPI generator already omits bodies for GET).
- For `POST` SSE endpoints, OpenAPI `requestBody` SHOULD include `inputPayload`.

## Observability (required)

Add spans/metrics analogous to command invoke:
- stream open (producer + consumer)
- chunk send/receive
- stream duration
- active stream count (gauge)
- errors by type/status

## Safety / stability limits (required)

To make this production-grade, we must enforce guardrails:

- `maxConcurrentStreams` per service instance (configurable)
- `maxChunkBytes` and/or `maxChunkRate` (configurable)
- aggregation guardrails:
  - aggregation MUST be opt-in
  - default `maxAggregatedChunks` (configurable) with a hard fail when exceeded

## Open Questions (must decide before implementation)

1. Stream completion on cancel: decided for v1 (terminal `cancel` frame).
2. Consumer-side validation toggle: do we expose `canConsumeStream(..., validateChunks = true)` or config-based toggle?
3. Ordering guarantees: do we guarantee ordering per session at the API level, or only best-effort with `sequence`?
4. Backpressure semantics: do we attempt transport-aware backpressure (where available) or define `write()` as best-effort async?
5. Timeouts: define defaults for:
   - overall TTL
   - idle timeout
   - heartbeat interval
6. Aggregation defaults: should default aggregate include more metadata (start/end timestamps, bytes)?
7. Info messages: do we need a new `InfoServiceStreamAdded`, or reuse `InfoServiceFunctionAdded` with a `kind: 'stream'` discriminator?
8. Final aggregate wire shape: do we send the aggregate only on `complete.final`, or also as an extra last `chunk` frame (user request wording)?
9. Context typing changes: do we add `Streams` as a new generic parameter to:
   - `CommandFunctionContext` / `SubscriptionFunctionContext`
   - `CommandDefinitionBuilderTypes` / `SubscriptionDefinitionBuilderTypes`
   to keep `context.stream` fully typed without `any`?
10. Stream handler style: do we support only `setStreamFunction(context,payload,params,writer)` or also async generator return (`AsyncIterable<Chunk>`)?
11. Control channel routing: confirm the per-instance (receiver.instanceId) control subscription approach for all bridges.
12. Limits defaults: choose default values for `maxConcurrentStreams`, `maxAggregatedChunks`, `maxChunkBytes`, and handshake timeout.

## Recommended defaults (if not otherwise decided)

These defaults are chosen to match existing Purista ergonomics (schema-driven typing + optional runtime validation) and to keep v1 implementable across all bridges.

1. Cancel semantics:
   - producer sends a terminal `cancel` frame (no `StatusCode`) and then stops (no extra `complete` frame).
2. Consumer-side validation toggle:
   - `canConsumeStream(..., validateChunks = true)` with default `true`.
3. Ordering:
   - treat per-session ordering as required; if out-of-order `sequence` is detected, fail the stream with an `error` frame.
4. Backpressure:
   - `writer.write()` is async; where the transport can signal backpressure/confirm publish, await it; otherwise resolve immediately.
5. Timeouts:
   - handshake timeout: 10s
   - idle timeout: disabled by default (opt-in)
   - heartbeat: 15s when HTTP-exposed, optional for broker-only consumption
6. Aggregation default:
   - `final` is sent only on the `complete` frame (not as a `chunk`).
   - default aggregate: `{ chunkCount, chunks }` with a hard cap `maxAggregatedChunks`.
7. Info messages:
   - add a dedicated `InfoServiceStreamAdded` so HTTP servers can add SSE endpoints without colliding with existing command routes.
8. Handler style:
   - v1 supports the writer style only; async generator support can be added later without breaking the protocol.
